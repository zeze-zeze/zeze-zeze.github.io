## Challenges

這次比賽我有參與的題目是 Pipin、bbbttfb，兩題都是 Attack & Defense。主辦方的題目會提供每隊各自的服務，讓參賽者從對手的服務拿分，同時要防守對手從自己的服務拿分。

<br/>

### Pipin

主辦方給了 [pipin-0ee4dc1e9d85d12778b30927f52bc0e7376c4a75.tar.gz](/assets/defcon-ctf-2026/pipin-0ee4dc1e9d85d12778b30927f52bc0e7376c4a75.tar.gz)，裡面放著一包 Unity 做的 Linux 2D 遊戲，最簡單的執行方式是直接 `./Pipin`。

遊戲是一隻圓圓可愛的鳥要走到終點，左右控制方向、空白鍵跳躍、E 跟物品互動，走到終點就會給 flag 拿分，玩起來像這樣:

<video src="/assets/defcon-ctf-2026/play-game-normally.mp4" style="max-width: 100%; width: 560px; height: auto; display: block;" controls preload="metadata" playsinline></video>

<br/>

一些比較明顯的遊戲設定:

- 鑰匙、彈簧其實是能推動改變位置的
- 死亡後會退回上一個 checkpoint
- 把鑰匙推到刺上，然後踩在鑰匙上不會扣血
- ...

<br/>

題目有給個 README.md，裡面提到遊戲的其他載入方式:

```
`./Pipin` runs the game.
`./Pipin --load-state lock.pipstate` loads a state file fetched from another team's service.
`./Pipin --check-input input.json` runs a given input. Use `-batchmode -nographics -logFile -` to run headless.
```

<br/>

#### Attack

`nc <ip> <port>` 後會取得一串 base64，decode 後是一坨 binary，這是給遊戲載入的 lock.pipstate，透過 `./Pipin --load-state lock.pipstate` 會從這個遊戲狀態開始遊玩。

之後要傳 input.json 的 base64 給 server，內容是一系列的玩家操作，遊戲會解析 input.json 後照著輸入的玩家操作移動，最後檢查是否成功到達終點，有的話 server 就會給 flag。

```json
{
    "format": "pipin-tas-v1",
    "level": "main-v1",
    "tickRate": 60,
    "runs": [
        {
            "ticks": 68,
            "held": [
                "right"
            ]
        },
        {
            "ticks": 22,
            "held": [
                "right",
                "interact"
            ]
        },
        {
            "ticks": 10,
            "held": [
                "right"
            ]
        },
        {
            "ticks": 41,
            "held": [
                "right",
                "jump"
            ]
        },
        ...
    ]
}
```

<br/>

#### Defense

防守方式主要是 lock.json，它跟 Attack 的 input.json 的格式一樣都是一系列的玩家操作，差別在於它的用途是把角色移動到其他地方，服務會根據移動後的位置產生 lock.pipstate，別隊要取得我們的 flag 就要從那個地方開始走到終點。

另外為了確保防守方給的 lock.json 是有解的，所以還要給個答案 input.json，從 lock.json 走到的地方開始走到終點。當然防守方的 input.json 不會透漏給其他隊伍，會給的只有 lock.pipstate。

<br/>

#### 比賽第一天解題狀況

題目剛出來時場面有點混亂，主要是不知道題目要我們做什麼，花了不少時間摸索才知道這題的攻防方式是要給玩家操作的 json。

在知道攻擊方要給答題的玩家操作 input.json，防守方要給出題的 lock.json 與答案的 input.json 後，面對的第一個問題就是玩家操作的 json 檔案要如何產生?

遊戲的主要邏輯都在 GameAssembly.so 中，開 IDA Pro 接好 MCP 跟著題目敘述一起丟給 AI 分析後，我讓它產生能夠把玩家的操作轉成 input.json 的腳本 [pipin_capture.py](/assets/defcon-ctf-2026/pipin_capture.py)。這是最初版的錄製腳本，直接偵測系統的鍵盤輸入，簡單的操作沒什麼問題；後來因為每一隊都在濫用遊戲的 glitch，導致 tick 的精確度變重要，所以隔天隊友又重寫了一版透過 frida hook 產生玩家輸入的腳本。

```
./Pipin # 執行遊戲
python3 pipin_capture.py # 開另一個 temrinal 跑錄製腳本，然後玩遊戲
```

現在能產生 lock.json 和 input.json，但是遊戲要求輸入的是 lock.pipstate，為了驗證我們的 patch 的 input.json 確實可以解 lock.json，所以還需要把 lock.json 變成 lock.pipstate 的轉換工具。讓 AI 生出 [pipin_dump.py](/assets/defcon-ctf-2026/pipin_dump.py)，利用 frida 來 hook function 輸入 lock.json 輸出 lock.pipstate。

```
python3 pipin_dump.py --lock lock.json # 跑完後產生 lock.pipstate
```

最初重工的問題十分嚴重。一開始接收到的資訊是要趕快弄出一版能解出初始版本遊戲的 input.json，當我們終於把能解出初始版本遊戲的 input.json 錄製出來後才發現隊友已經做完了；後來又接到需求要做出一版基本的 patch，至少把角色位置移到其他地方，別讓其他隊用最簡單的 input.json 從我們隊拿分，又花了時間產生 lock.json、input.json 之後，才發現其他隊友又做好一樣的事。

隊長和這題的 PM 後來把跟解這題相關的隊友都拉到同個小房間後，溝通成本才降低許多。

但是等到狀況稍微穩定時，第一天也快結束了，在最後幾回合才草草的手動打來拿分。分數有但不多，總之這題第一天的得分狀況不太理想。

<br/>

#### 比賽第一天晚上寫作業

晚上大家開檢討會議，決定負責這題的人選。分工之後，有人負責把自動化解題腳本放到我們的 attack manager 做自動化、把 patch 上我們的 workstation；有人做自動解題腳本；有人研究遊戲的 glitch，做出更難的 patch。

研究出的更難的 patch 又可以拿去測試自動解題腳本，改進自動解題腳本，形成良性循環。

分析遊戲後，整張遊戲地圖如下:

![image](/assets/defcon-ctf-2026/map.png)

可以發現在角色初始位置的左邊還有一大塊空間，這是正常玩法過不去的地方，但既然這個地方存在，就肯定有能過去的方法。在分析 GameAssembly.so 後，發現了很多 glitch，利用遊戲中一些沒處理好的判斷邏輯，造成在正常情況下遊玩無法達到的操作，例如:

- 彈簧雙重疊加 Super Jump: 彈簧的觸發方式是 vy = max(vy,0) + 24 疊加而非指定值，在飛出互動範圍前再觸發一次可以跳更高。
- 繩索擺動加速: 掛在繩索上沿著當前切線方向前進能無限累加速度。
- 對角 Corner Bypass: 遊戲的對角移動是先水平掃描位移，再垂直掃描位移，在牆角高速斜衝可從新 X 座標穿過牆面。
- 從開過的門能取得一把鑰匙: PIPSTATE 不序列化鑰匙，所以可以關掉並憑空退回一把鑰匙。
- NPC 對話傳送: 對話時會執行 Teleport(player.x, -9999)，接著被重生回 checkpoint 並補滿血。
- 掛上繩索時速度重計: 重新掛上繩索會把切線速度設為預設值，這能當作高速衝刺後的煞車方法。
- ...

遊戲還有其他的 glitch，但第一天晚上知道的大概就這些，其他是第二天看其他隊的 patch 才知道的。

至於解題腳本的部分，是讓 AI 生的，原理大概是:

1. 把遊戲本體當成 oracle: 用 LD_PRELOAD hook 進 Unity，開一個 socket，可以從任意存檔點分支跑一段輸入再存檔。等於得到一棵可任意 backtrack 的狀態樹。
2. 依賴一條已知通關的 reference TAS: 收到 lock 的 .pipstate 後，先算它最像 reference 的哪一 tick，然後直接把那之後的 reference 輸入接上去試跑。
3. 嘗試各種解法: 依序試短的正規化前綴，最後才用 beam search 找一小段 bridge 把狀態拉回已知的路徑。
4. 驗證: 開一個遊戲 process 用 `--check-input` 測試，確認能走到終點。

想說已經做出我們自認最強的 patch，而我們的自動解題腳本也能應付我們已知的各種 patch，所以就安心的迎接第二天比賽。

#### 比賽第二天

第二天剛開始解題腳本原本能解開每一隊的 patch，但是過了幾回合其他隊開始上新的 patch 後，解題腳本能解開的隊伍數就漸漸減少。主要原因是有些隊伍的 patch 走到的遊戲狀態是解題腳本不認識的 state，也走不回已知的路徑。

後來這題的狀況變成有隊友負責電競，用寫好的外掛腳本手動玩遊戲，把成功通關的玩家操作輸出後提交給我；有隊友負責修解題腳本，盡量讓解題腳本能解出更多不同的 state；我的部分則是在拿到隊友的玩家操作 json 後送給 server 一隊一隊拿 flag，拿到 flag 後提交，成為妥妥的一個交 flag 機器，以及負責上 patch、同步隊友之間的狀態，避免重工。

### bbbttfb

這題算是比較傳統的 pwn 的 Attack & Defense，主辦方給一份 [image-rootfs.zip](/assets/defcon-ctf-2026/image-rootfs.zip)，主要的目標是裡面的 netscape 瀏覽器 `/opt/netscape/netscape.elf`，它是個 32-bit 的 ELF，裡面有一堆漏洞，而且預設沒有開啟任何保護機制。

由於我加入這題已經是第二天結束了，沒參與到題目剛出來時的狀況，所以直接進入第二天晚上寫作業的環節。

<br/>

#### Attack

`nc <ip> <port>` 之後就可以跟 netscape 瀏覽器互動，送封包給它，利用漏洞讀出 flag，flag 的位置在 `/flag`。

<br/>

#### Defense

對 netscape.elf 做各種修改，例如修補 netscape.elf 中的漏洞、增加 binary 保護機制 (NX、PIE、ASLR、...)，甚至是加殼、混淆。

每回合都會看各隊的防守狀況，只要自己的隊伍沒有被其他隊成功拿 flag，就可以獲得防守分數。

<br/>

#### 比賽第二天晚上寫作業

在第二天晚上我們準備好幾個不同漏洞的 exploit，漏洞列表如下:

- 在解析 HTTP 封包的 Expires、Last-Modified、Set-Cookie 的 header 值時 sscanf 有 stack-based buffer overflow
- 在 HTTP 重導向解析 hostname 時 sprintf 有 stack-based buffer overflow
- 在解析 HTTP 401 auth realm 時 sprintf 有 stack-based buffer overflow
- 在處理 HTTP 的 Content-Length 時有 integer overflow
- 在 XBM decoder 有 Out-of-bounds Write 導致任意寫
- 在處理 NNTP response 時的 sprintf 有 stack-based buffer overflow
- 在解析 FTP 封包的 USER、PASS、RETR、目錄路徑時有 stack-based buffer overflow

patch 的部分因為聽說 SLA (Service-Level Agreement) 很嚴格，所以隊友準備了各種 patch，從只修補個別漏洞，到增加各種保護機制，在隔天確認哪些可以通過 SLA。

<br/>

#### 比賽第三天

第三天比賽剛開始時，在每隊都沒被 patch 的狀況下，互相都能拿到 flag。在過了幾回合，每隊的 patch 都差不多上了之後，能打的隊伍瞬間減半，而且隨著比賽時間能打的隊伍數漸漸減少。

不過基本上大部分隊伍都差不多，到比賽結束前幾乎每一隊能打的都只有少數一兩隊，甚至有隊伍直接開擺，沒打也沒防了，只有其中一兩隊可能找到了特別隱密的漏洞能通殺全隊。

patch 的部分不確定主辦方是不是有降低 SLA 的門檻，準備的 patch 都有通過 SLA，所以最後就使用我們準備的最強的 patch，包含把所有已知漏洞修補、套上所有保護機制的版本。上了 patch 之後大概剩五隊能成功從我們這拿到 flag。

後來看到第一名隊伍 BlueWater 的 patch 能完美防住所有隊的 exploit，所以最後改成使用 BlueWater 的 patch，賺些防守分。有趣的是，後來 BlueWater 自己更新 patch 後反而被其他隊成功拿 flag，而我們隊卻沒被打，因而獨佔幾回合的防守分。

這一天從早上 09:30 比到中午 12:00，整個賽程非常緊湊，賽中能做的就是瘋狂看其他隊 patch 什麼，想辦法繞過後拿 flag，還有看還能 patch 什麼來加強防護。

<br/>

## 賽後反省

在這個 AI 世代，由於實作門檻降低，我認為發現問題與定義問題的能力變得更重要。

雖然這次 X 上看到很多參賽者都抱怨比賽已經變成 AI 詠唱大賽，但我覺得既然變這樣就代表 AI 是現在的主流，資安技術本來就變動很快，我們只能去適應變化。

當然參賽者能否像以前一樣享受比賽以及從比賽中學到東西則是另一回事。
